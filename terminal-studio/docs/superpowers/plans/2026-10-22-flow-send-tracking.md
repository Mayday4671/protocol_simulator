# 直接发送与流程跟踪联动

问题：选择流程只显示步骤，普通「发送报文」不创建观察运行。用户已收到注册应答，时间轴仍全部显示未执行。旧 EXE 的真实 UDP 回归已复现。

行为：选择流程后，发送该流程首个发送步骤的信令时，先建立手动观察运行，再发送。已有同流程、同通道的活动运行时复用；完成后再次发送首步创建新记录。未选择流程、无关信令、以接收起步的流程不隐式创建运行。接收起步可用原有「手动跟踪」。不回放历史报文伪造当前进度。

- [x] 新增客户端回归：未点手动跟踪直接发送，在旧 EXE 中观察到时间轴无运行记录。
- [x] 发送入口等待跟踪器准备完成；普通发送与周期发送共用，错误时停止发包并提示原因。
- [x] 跟踪器通过实时运行状态避免重复启动，通过启动中的 Promise 合并并发启动。
- [x] 最终 EXE 回归：无设备档案选择、抽屉收起时，手动六步真实 UDP；不选流程不启动；完成后首步重新开始；保留自动运行。
- [x] 打包新 NSIS 安装程序并记录验证结果。

验收：`native_flow_send_tracking.cjs`、`native_iot_walkthrough.cjs` 通过，真实 UDP 观察到首步自动创建跟踪、后续步骤共用运行、重新发送首步创建新记录；原有自动运行及显式手动跟踪均通过。`ui_flow_drawer.cjs` 通过，增加未选流程/无关协议不启动、并发准备共用启动请求、启动异常向发送方传播的检查。TypeScript、Vite、Windows release、NSIS 打包通过。

安装包：`release/Simulated-Terminal_0.1.0_flow-send-tracking_20261022_x64-setup.exe`。未覆盖安装用户正在运行的客户端；本次未修改用户数据库。截图与事件：`artifacts/flow-send-tracking/`。
