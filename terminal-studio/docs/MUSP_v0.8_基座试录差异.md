# MUSP v0.8 无人机协议：原版基座试录

导入 `protocols/MUSP_v0.8_无人机联调_基座试录.xml`，系统名为 **MUSP v0.8 无人机联调（基座试录）**。共34条信令，分注册认证、配置心跳、状态业务、呼叫、资源与结束五组。本次仅转换协议数据，未引入旧引擎或旧UI，未更改原始业务基线。

**这不是完整MUSP适配。** 配置请求0x21和响应0x22现使用动态数组，业务体长度、总长度、发送CRC自动计算；其余信令仍是静态CRC样例，修改后须外部重算。总长度使用基座已有 `{tlen}`。客户端接收端的完整CRC/业务规则校验仍未实现。

## 已能直接检查

- 基础23B公共头按组配置，信令以 `header-ref` 覆盖头字段；全部业务字段仍可单独编辑，不是整帧HEX模板。
- 34个信令码保留，默认样例均有静态正确CRC；0x01注册、0x31心跳可编码。默认事务号固定00000065、地址00003B/000001、会话1234（注册请求0000），均为手工测试值，不宣称自动绑定运行会话。
- 0x21使用29B头（6B固定认证TLV），8B通用段属于业务体；模式01使用设备条目，模式02使用通道参数条目，每条10B，条目数控制数组。默认仍为模式02五条。0x22不包含8B段，其结果数组随数量变化，默认五个AA。
- 0x21/22逐字节匹配根目录 `docs/06_示例与测试数据/golden-vectors.json`：99B/D35D、31B/FECB。原业务讨论稿另有99B/EB46样例，其通道频率/功率数据不同，两者不可混用。本次明确使用golden向量。
- 枚举从原协议数据复制；0x22仅定义AA成功，不将00改称成功。其余返回码没有新造含义。
- 状态上报、离线通知的零条目数组使用现有 `{vlen}` / `unit` / `device_count` 定义，可展示子字段。但增加条目后必须人工重算业务长度与CRC。

## 未支持与试录取舍

|需求|原版基座能力/本次取舍|
|---|---|
|CRC-16/CCITT-FALSE联动及入站校验|配置请求/响应使用 `{crc16_ccitt_false}` 计算发送CRC。其他试录信令仍为静态值；客户端入站CRC校验未实现。模拟对端严格校验CRC。|
|bodyLength/headerLength计算、TLV按长度解析|配置请求/响应业务体使用 `{byte_length:起始字段名:CRC16}` 自动计算。头长度仍固定；认证TLV仅在0x21样例放置固定4B测试Token。其他认证变体未覆盖。|
|0x21模式01/02动态数组切换|两种模式分别定义10B的unit；条数改变可见条目及发送内容。编码器拒绝数量与内容不一致。未增加原规则以外的设备状态机。|
|0x22动态数量与请求条目逐项映射|结果数组随条数编码、解析；模拟对端按请求数量返回AA。客户端事务/地址/会话联合关联、原顺序应用、幂等提交未实现。|
|位编辑、BIN、单位、带符号解码、Token脱敏|基座字段主类型HEX，枚举可读；位域和单位语义仅描述，未支持独立位控件/完整多层解析。Token为公开测试值。|
|认证生命周期和响应字段提取|未配置。未写任何从响应取值占位符，不自动把手工值作为运行凭证。|
|自动应答和流程|未启用。静态CRC与事务回填不能可靠联动，故不配置会产生无效自动报文的流程。|
|原子配置、批次完整性、未知结果、并发超时|未支持MUSP业务状态机。Bit7/Bit0和AA保留原义，但不触发提交。|
|无人机三态、RX/TX分配撤销、结束闭环|字段已录入；资源核销、UNKNOWN、同callId多方关联等业务语义未支持。|
|入站严格结构验证|信令码路由及字段展示可试用；不保证同步头、版本、CRC、计数、总长全部校验，更不能以已识别代替已验证。|
|配置最多20条|协议规则仍是最多20条。当前通用条目编辑器上限为200，尚未配置协议专属上限；模拟对端会拒绝超过20条的请求。|

其他信令默认值只是用于编码检查的测试输入，来源无明确值时使用零值或已声明枚举首项，不宣称这些值能完成真实对端业务。0x51参数块默认空，业务Token默认固定4B；所有变长边界须另行验证。

## 验证入口

1. `python scripts/build_musp_trial.py`：从 `../docs/06_示例与测试数据/musp-v08-reference.xml` 读取字段定义并重建试录XML/静态样例JSON；校验两个golden向量。该文件保留原协议定义，不依赖旧工程备份，也不加载任何归档代码。
2. `python scripts/verify_musp_trial.py`：独立检查34条静态样例的长度/CRC和golden。
3. `cargo test --manifest-path src-tauri/Cargo.toml -p simterm-core --test musp_trial_import`：使用当前基座XML解析器、公共头合并、字段渲染器检查全部34条实际输出，并验证golden及CRC。此测试只验证默认静态编码，不验证修改后的动态CRC能力或UDP业务闭环。

测试文件：`src-tauri/core/tests/musp_trial_import.rs`；测试结果由执行者报告。本说明不将未运行的Cargo测试记为通过。

- 真实UDP通道：127.0.0.1:39001 → 本机测试对端127.0.0.1:39002。客户端发送0x21得到99B且逐字节匹配golden，对端返回31B的0x22；同页收发及字节布局解析显示五个AA配置成功，HEX/十进制/中文可见。

## 协议配置中的条件与数组

协议编辑按定义序号排列，只有连续且条件相同的字段合并展示。0x21 的模式目标地址后仍是配置版本、保留字节，再到对应模式的数组；相隔公共字段的同条件段分别显示。此前界面把第17和21项、第18和22项提前合并，显示顺序与真实编码顺序不一致，现已修正；协议数据顺序不变。

数组行的“单条 10 B”表示一条记录长度；“5条默认数据 · 50 B”表示已有默认数据的总量，两者含义不同。“条目结构”直接展开子字段，完整默认HEX放在“默认条目数据（HEX）”内，可单独展开编辑。修改结构不自动重写已有默认HEX；保存仍检查数据是否包含完整条目。控制台的实际条数继续由协议的条目数字段控制。
