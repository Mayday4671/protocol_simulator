# 自造复杂物联网协议验收

测试文件：`STRESS_IOT_1.0.xml`。两个系统、两个分组、四条协议。不是任何厂商的真实标准。

环境采集系统包含双列表条件配置，以及设备列表内嵌测点列表；门禁系统包含普通字节协议和位段控制协议。位段控制的 `<bit-field>` 是待实现的需求表达，不是当前已经支持的 XML 语法，专门检查不支持的结构是否被静默丢弃。

在 `src-tauri` 目录执行：

```powershell
cargo run -p simterm-core --example capability_probe
cargo run --features e2e --bin e2e_isolation
```

第一条命令在存在能力缺口时返回 1；第二条使用独立内存库和本机 UDP，不接触正式数据库。不要把两条命令的最后一个退出码当成全部测试通过。

## 本次实际结果

- 通过：模式 01 与模式 02 分支组包、两个独立列表及尾部解析、零条目、另一系统的 UInt/ASCII 混合编码，共 6 个检查。
- 不满足：bit 组包与 bit 条件分支，期望 `31D30AEF`，实际 `3100EF`。
- 不满足：导入器接受带未知 bit 子元素的协议，但字段模型未保留该声明，也没有拒绝导入。
- 不满足：嵌套变长列表解析，报文 `0201021122020133EE` 的尾标应为 `EE`，实际识别为 `33`。
- 不满足：只提供列表结构和默认值时，核心直接发出 `3101020155AA`，未生成数量声明的记录；目前普通列表需要界面或调用方先拼 Hex。
- 通过：真实 UDP 的 A/B 注册、未注册终端、跨系统会话隔离、切回 A、向 B 推送请求后自动应答、周期任务使用新会话、停止任务清理。

这不是完整压力/吞吐测试，也不证明相同线格式的不同协议可自动区分。当前结论是：普通字节协议和已编码的条件列表可用，但不能满足完整的复杂结构化多协议需求。分支组展示和页面页签不属于这个核心探针的验收范围，仍需实现与交互验收。
