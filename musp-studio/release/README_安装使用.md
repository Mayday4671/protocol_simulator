# MUSP Studio 0.1.0 安装与使用

面向 Windows 10/11 x64。应用在本机执行协议解析、真实 UDP 收发、流程调度和 SQLite 存储；安装后的使用不需要 Node.js、Rust、Java 或数据库服务。

## 发行状态与文件校验

NSIS 安装包 `MUSP-Studio_0.1.0_x64-setup.exe` 已实际构建（213.75 MiB），采用当前用户安装、中文/英文界面，并内嵌 WebView2 离线安装器。本机 Windows 10 的安装、升级、安装后真实UDP自测、七页界面及卸载保留数据验收通过，详见同目录 `test-report.html`。尚未验证全新且未安装WebView2的离线虚拟机。此版本未配置代码签名；SHA256用于完整性校验，不是发布者签名。

发布方应随实际 Setup.exe 提供 `SHA256SUMS.txt`，每行格式为 `64 位 SHA256`、两个空格、文件名。清单文件名必须相对本目录，不能包含 `..` 或绝对路径。校验整个清单：

```powershell
powershell.exe -NoProfile -File .\verify.ps1
```

也可对照另行取得的期望值校验一个文件：

```powershell
powershell.exe -NoProfile -File .\verify.ps1 -FilePath '.\实际安装包名称.exe' -ExpectedSha256 '替换为64位期望SHA256'
```

脚本只读取文件并计算散列，不安装、不启动应用，也不删除或修改用户数据。退出码 `0` 表示全部一致；非零表示清单/文件错误或不一致。若 PowerShell 执行策略阻止脚本，可直接运行 `Get-FileHash -Algorithm SHA256 -LiteralPath '.\实际安装包名称.exe'` 与清单比对。

## 安装、数据与卸载

1. 校验通过后运行实际 Setup.exe，按向导安装并启动 MUSP Studio。安装路径以向导显示值为准。
2. 首次打开会建立本地项目、一个参与系统和 MUSP v0.8 协议发布样例；设备、通话、资源池与运行结果不会预置。
3. 在“系统设置 → 项目与存储”查看真实数据目录。数据库为其下的 `db/musp.db`，导出文件在 `export/`；协议编辑副本在 `projects/`。
4. 升级或卸载前，可在工作台/系统设置导出项目 ZIP，并在报文监控另行导出 JSONL。项目 ZIP 包含协议、流程、业务配置等，不包含全部报文历史或可恢复认证 Token。需要完整本地备份时，先退出应用，再复制整个数据目录。
5. 通过 Windows“已安装的应用”或安装目录中的卸载程序卸载。默认不勾选清除应用数据时保留项目；已实测静默卸载后SQLite仍在且内容散列不变。主动勾选清除数据会删除本地项目，请先备份。

退出会停止监听；重开不会自动重发之前流程。设备需重新注册，未完成释放的资源恢复为 UNKNOWN。切换项目之前要停止端点和运行中的流程。

## 安装后二进制自测

自测直接运行安装后的 EXE，不依赖开发服务器。**必须使用新建的隔离目录，不要指定日常工作数据目录**；自测会在指定目录建库、配置设备并写入报文。

```powershell
$exe = 'C:\替换为实际安装目录\musp-studio.exe'
$testDir = Join-Path $env:TEMP ('musp-install-check-' + [guid]::NewGuid().ToString('N'))
$process = Start-Process -FilePath $exe -ArgumentList @('--self-test', ('"' + $testDir + '"')) -WindowStyle Hidden -Wait -PassThru
$process.ExitCode
Get-Content -LiteralPath (Join-Path $testDir 'self-test.json') -Raw
```

成功输出包含 `passed: true`，检查覆盖 SQLite 初始化、内置 XML 编译、真实回环 UDP 双端点、编码/CRC、响应唯一匹配、`0x22` 业务提交和报文入库。退出码：`0` 成功，`1` 自测失败，`2` 未提供目录，`3` 无法写入结果。此测试不覆盖 NSIS 安装器、卸载、WebView2 缺失场景、UI 全流程或外部硬件兼容性。

`--inspect-local` **仅用于本地测试排查**：正常 GUI 启动附加该参数会在 `127.0.0.1:9223` 启用 WebView 调试端口。日常使用不需要此选项，也不要将它加入正常启动快捷方式。它与 `--self-test` 是不同入口。

## 七个业务页面

| 页面 | 使用入口 |
|---|---|
| 工作台 | “新建监听”、端点启动/停止、设备/流程统计、项目导出 |
| 协议设计 | XML 和结构编辑，“保存草稿”“校验”“校验并发布” |
| 设备管理 | 手动创建、三字节地址、所属系统、配置参数、协议身份 UUID |
| 交互流程 | 复制模板、拖拽连线、节点 JSON、“校验并发布”“启动流程”、运行轨迹 |
| 报文监控 | 选择发布协议、业务 JSON、“编码”“解析 HEX”“发送一次”、真实 RX/TX |
| 通话资源 | 创建资源池、复制池 UUID、逐方向状态、结束通话、UNKNOWN 核实 |
| 模板库 | 七个业务模板“复制到项目并编排”、协议版本和 XML 编辑 |

“系统设置”是另一个管理入口。设备只有“离线 / 在线 / 通信”三态；流程“等待 / 超时 / 失败”等不混入设备状态。“本地发送成功”只代表 socket 接受了发送，不代表远端业务成功。报文监控的“暂停刷新”不会停止 UDP 收包。

## 跑通配置五设备 → 注册 → 心跳

以下使用两个真实回环 UDP socket，不需要外部硬件。端口可换为本机未占用端口。示例数值仅用于本地联调。

### 1. 建立两个端点

在工作台分别“新建监听”，两者都选择同一个已发布的 **MUSP v0.8 业务样例**：

| 名称 | 本机绑定 | 本地 Rust UDP 对端 |
|---|---|---|
| 工作端 | `127.0.0.1:9001` | 不勾选 |
| 应答端 | `127.0.0.1:9002` | 勾选 |

故障注入先全部关闭。应答端按收到的真实协议报文回应，不会主动替你发送通话申请。真实硬件联调时，把远端地址换成实际设备地址，并按实际网络选绑定地址。

在系统设置复制当前“系统 ID”。手工完成后续步骤可能超过默认 30 秒心跳超时；仅为这轮本地联调，可先将“心跳超时”设为 `0` 关闭自动超时，做完再恢复所需策略。会话许可自身的有效期仍需遵守。

### 2. 配置五台设备

在模板库选择“五条配置映射五台设备”，点击“复制到项目并编排”。进入交互流程后：

1. 保留模板默认变量，在“运行变量 JSON”对象中加入 `"systemId": "实际系统UUID"`；不要把说明文字当成 UUID。
2. 确认协议绑定为两个端点使用的同一发布版本。选择“工作端”，远端填 `127.0.0.1:9002`。
3. 点击“校验并发布”，再“启动流程”。
4. 查看运行实例/轨迹和报文监控：实际发出 `0x21`，收到 `0x22`，五条结果均为 `AA`，流程完成后设备列表出现 `00 00 3B` 至 `00 00 3F` 五台设备，状态仍为离线。

仅收到原始报文、响应数量错误或未正确匹配时不会提交配置。非 `AA` 不是已确认成功。对这些设备再次配置不得清空已有注册或通话状态。

第二个配置模板“五条配置映射单设备五组参数”使用 `configMode=2`，目标默认 `00 00 3B`。在已存在该设备后，以相同端点、系统变量运行，五条通道参数写入一个设备，不新增五台设备。频率、功率等示例值可在节点完整 JSON 中调整后重新发布。

### 3. 注册

复制“注册—无需认证模式”，加入实际 `systemId`，工作端/远端同上。默认 `deviceAddress` 为 `00 00 3B`、`deviceNumericId` 为十进制 `59`。发布并运行后，依次发生 `0x01/0x02` 和 `0x03/0x04`；成功后该设备进入在线。

在报文监控选择该次 `0x02` 或 `0x04`，记下字段树中的 **Session ID**（需要时看十进制解释），供后续心跳/通话使用。模板中的 `1` 是示例，不能代替真实返回值。若对端返回 `authMode=1`，此模板会失败，应改用“注册—独立认证下发”，不能跳过认证。

视频需要第二台设备。再次运行此注册模板，把 `deviceAddress` 改为 `00 00 3C`、`deviceNumericId` 改为 `60`，记录 B 的实际 Session ID。A/B 可以共用此联调应答端，逻辑地址和会话仍分开匹配。

### 4. 心跳

复制“已注册设备的三轮心跳”，填写实际 `systemId`、`deviceAddress` 和刚获得的 `sessionId`，仍选择工作端 → 应答端。发布并运行，三轮 `0x31/0x32` 往返后完成。模板为有限循环，不会永久保活；需要持续保活时应显式设计循环上限和运行时长。

心跳不会把已经离线的旧会话重新变为在线；超时或重新打开应用后先重新注册。

### 外部控制端要求认证时

复制第七个模板“注册—独立认证下发”，填写实际 `systemId`、设备内部 UUID `deviceId`、`deviceAddress` 和 `deviceNumericId`，选择实际工作端与外部控制端地址，再发布运行。内置本地 Rust 应答器使用 `authMode=0`，不会替这个模板制造认证下发。

外部控制端需对 `0x01` 返回 `authMode=1` 的 `0x02`，分配非零会话号；随后用新事务发送同一端点/协议/对端/设备/会话的 `0x11 AUTH_ISSUE`。应用实际发出同事务的 `0x12 AUTH_ACK` 后，模板取出有效 Token，以新的注册事务和认证扩展发送 `0x03`，最后等待对应 `0x04`。认证下发早于等待节点也会保留就绪事件；未收到下发、Token 过期或作用域不符会失败，不会直接标在线。Token 只保留在内存，日志与报文导出会脱敏。

## 跑通视频四资源 / 语音两资源

这两个模板是**控制侧响应流程**。先启动等待，再从应答端发来申请；单击启动并不会凭空生成通话。

### 前置条件和变量

1. 按上节完成 A 的注册；视频另需 B 注册。设备管理 → 详情 →“协议身份”复制内部 UUID，分别作为 `deviceAId`、`deviceBId`。这不是协议地址，也不是 Session ID。
2. 在通话资源点击“创建资源池”，例如名称“本地联调”、容量 `20000`、单位 `kbps`，复制新生成的资源池 UUID 为 `poolId`。
3. 复制“控制侧视频寻呼与四项资源”或“控制侧语音许可与两项资源”。在原有变量对象中补齐下表；工作端和远端仍是 `9001 → 9002`。示例频率、带宽应按对端能力编辑。

| 变量 | 视频 | 语音 |
|---|---|---|
| `systemId` | 当前系统 UUID | 同左 |
| `deviceAId` / `deviceAAddress` | A 内部 UUID / `00 00 3B` | 同左 |
| `sessionA` | A 真实会话号 | 同左 |
| `deviceBId` / `deviceBAddress` | B 内部 UUID / `00 00 3C` | 不需要 |
| `sessionB` | B 真实会话号 | 不需要 |
| `poolId` | 实际资源池 UUID | 同左 |
| `calleeNumericAddress` | `60`，必须与 B 的 `00 00 3C` 一致 | 不需要 |
| `wireCallId` | 默认 `8193`；每个并行通话选择不同值 | 默认 `8194` |
| `assignedRxKbps` / `assignedTxKbps` | 默认 `512 / 2048`，每位参与者各一组 | 默认 `64 / 64` |
| `startMode` | `CONTROL_NOTIFY` 或 `LOCAL_READY` | 同左 |

`endpointId` 和 `remote` 由启动区选择填写；不需要把端点名称手写进变量。所有关联报文必须使用同一发布协议版本。参数改动完成后“校验并发布”，再启动流程，看到 WAITING 后发送申请。

### 从另一端点发送真实申请

进入报文监控，“报文构造与发送”选择相同发布协议，本地发送端点选择**应答端 9002**，远端改为 **`127.0.0.1:9001`**。视频信令码填 `60`（HEX），业务 JSON 如下；把 `sessionId` 换为 A 的实际会话号：

```json
{
  "srcAddr": "00 00 3B",
  "dstAddr": "00 00 01",
  "transactionId": 1001,
  "sessionId": 1,
  "body": {
    "calleeAddr": 60,
    "mediaType": 2,
    "requestTxKbps": 2048,
    "requestRxKbps": 512,
    "codecFlags": 3,
    "priority": 1
  }
}
```

点击“编码”后“发送一次”。视频流程收到 `0x60`，对 B 执行 `0x62/0x63` 寻呼，之后按协议发送许可/通知，并分别完成 A.RX、A.TX、B.RX、B.TX 的资源配置和 `0x72` 确认。CONTROL_NOTIFY 还需 `0x75/0x79`，全部必要条件满足才进入 ACTIVE。LOCAL_READY 使用逐资源确认后的本地就绪规则。

语音先启动对应模板，再用信令码 `65`、新的事务号（例如 `1002`）发送：

```json
{
  "srcAddr": "00 00 3B",
  "dstAddr": "00 00 01",
  "transactionId": 1002,
  "sessionId": 1,
  "body": {
    "serviceType": 1,
    "requestTxKbps": 64,
    "requestRxKbps": 64,
    "codecType": 1,
    "priority": 1
  }
}
```

仍须替换真实会话号。语音不走视频寻呼，成功后只有 A.RX、A.TX 两项资源。两种通话可并存，池容量按各自资源扣减；示例默认分配下视频占 `5120 kbps`，语音占 `128 kbps`。

### 结束、掉线和 UNKNOWN

在通话资源选择一条通话并“结束此通话”，观察停止通知和逐项 `0x76/0x77` 释放。只结束此 call，其他 call 不受影响。收到正确确认才回池；应答端停止、超时或缺少确认时，资源保持 UNKNOWN 和占用容量。

也可从 A 或 B 所在的真实对端发送 `0x73`，使用该设备当前会话、原来的控制端目标地址，以及 `body: {"callId":8193,"reasonCode":0}`（替换为实际通话号）。应用返回对应事务的 `0x74`：`00` 是受理，`03` 是正在结束；资源仍需逐项 `0x77`。A/B 同时发起不会重复清理。收尾后会向仍有效的参与方发送 `0x7A`，其中未核实资源计数来自实际状态。

尚未建立通话、没有可用通话号时，申请方可用新的事务发送 `0x7B`，业务体为 `{"originalTransactionId":1001,"cancelReason":0}`，原事务号应等于本次 `0x60` 或 `0x65` 的事务。`0x7C` 的 `00` 表示取消受理、`01` 表示找不到原申请、`02` 表示已建立，应改发 `0x73`。已分配的资源继续独立清理；迟到寻呼或配置响应不会重启已取消流程。

“核实释放”仅用于外部确实已经释放的 UNKNOWN 资源，必须填写依据并勾选确认，后端记录审计；它不是伪造远端 ACK 的按钮。掉线或停止流程不等于所有远端资源已经释放。

## 常见定位与业务待确认项

- 端口绑定失败：确认端口未被其他实例占用，或换端口后同步修改远端地址。防火墙与网卡范围需与联调环境一致。
- 没有响应：先查看是否真正发出了 TX、对端是否启用、源/目标端口是否相反；再看 CRC/长度诊断、发布版本、源/目标地址、事务和会话。流程已超时后到达的响应不会自动完成旧运行。
- 配置成功但仍离线：这是预期状态，配置与注册分离；执行有效注册后才在线。
- 通话停在等待：确认先启动控制流程，再从另一个端点发送 `0x60`/`0x65`，并核对实际 Session ID 和远端地址。
- `configCommon8` 的部分位/保留字节语义尚未由业务方最终确认；当前 XML 中的候选解释可编辑，不能当作新增协议事实。`CONFIG_RESULT` 仅 `AA` 已确认成功，其他值保留原码，不补造失败枚举。
- 配置映射（多设备/单设备参数）、生效策略及 LOCAL_READY / CONTROL_NOTIFY 需按具体场景明确选用；内置模板是一组可运行样例，不代表所有现场设备必然采用相同策略。
- 原始讨论稿标题含 v0.7，交付业务基线按 v0.8；原文未被改写。认证算法与现场控制端策略、具体现场参数和外部设备兼容性仍需联调确认。
